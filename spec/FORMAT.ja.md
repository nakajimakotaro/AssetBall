# AssetBall format v1

[English](FORMAT.md) | 日本語

## ファイル

`index.json` は UTF-8 JSON（出力は BOM なし、LF）です。`version` は形式の版であり、リリース番号ではありません。Ball 名は `ball-<UTC日時>-<SHA-256>.bin` とし、日時は固定桁の `yyyyMMddTHHmmss.fffffffZ` 形式で記録するため、ファイル名の辞書順が日時順になります。日時は Ball の書き込み後に付与し、同時刻の異なる内容はハッシュで区別します。同じ入力と前回 Index から Ball のバイト列と配置は再現できますが、ビルドごとに新しい日時が付きます。絶対パスは含みません。

```json
{
  "format": "assetball",
  "version": 1,
  "hashAlgorithm": "sha256",
  "ball": {
    "file": "ball-20260918T072345.1234567Z-e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855.bin",
    "size": 0,
    "hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
  },
  "assets": []
}
```

各 `assets` 要素は `path`、`offset`、`size`、`hash` を必須とします。数値は非負の符号付き64ビット整数。範囲は `[offset, offset + size)` です。HTTP には `bytes=offset-(offset+size-1)` として渡します。長さ0のアセットは Range を発生させません。

Ball にヘッダー、パディング、圧縮、ファイル名等は入りません。`assets` の順序が Ball 内の順序です。各 `hash` はそのアセットの生バイト列の SHA-256、`ball.hash` は Ball 全体の生バイト列の SHA-256 を小文字64桁16進数で表します。S3 の Multipart composite checksum は `ball.hash` と別物です。

## 検証

[JSON Schema](index.schema.json) に加えて、実装は次を検査します。

- `format` / `version` / `hashAlgorithm` が対応値であること。
- `ball.file` は文字・数字・`-`・`_`・`.` のみを含む単一の `ball-*.bin` ファイル名であること。名前に含まれる日時やハッシュは検証せず、内容の整合性は `ball.hash` で検証する。
- パスが空でなく、相対 `/` 区切りであること。空要素、`.`、`..`、バックスラッシュ、コロン、制御文字を拒否。
- パスの大文字・小文字を区別した一意性。Unicode 正規化は実施しない。
- 最初のオフセットが0、その後は直前の末尾。穴・重なり・オーバーフローを許可しない。
- 最後の末尾と `ball.size` が一致すること。
- JSON の必須フィールド欠落、不適切な型、重複プロパティを拒否。未知フィールドは無視。
- 入出力 Index の最大サイズは64 MiB。Ball の検証では実サイズ、全アセットのハッシュ、全体ハッシュを検査。

同一内容を持つ異なるパス間の重複排除はしません。全ファイルを保存するため、リネームは削除＋追加として扱います。

## 配置・転送アルゴリズム

1. 入力をパスと SHA-256 / サイズで比較する。
2. 未変更エントリーを前回の Index 順に並べる。
3. 変更・追加エントリーを `StringComparer.Ordinal` のパス順に末尾へ並べる。
4. オフセットを0から詰め直し、削除エントリーは出力しない。

`Planner.Layout` は前回 Index とスキャン結果のみを扱い、I/O しません。`Planner.Compare` は更新前後の Index からコピー元／先／長さと不足範囲を計算します。ローカルコピーはコピー元とコピー先の両方が連続する場合のみ結合します。不足範囲はコピー先が連続すると結合します。

S3 の `MultipartPlanner` はこの共通コピー範囲を制約内の Part へ変換します。変更量と制約による再アップロード量を分けて報告します。S3 固有制約は Core へ持ち込みません。

## 公開方式の判断

単一の固定 Ball 名を上書きすると、古い Index を取得済みのクライアントが新しい Ball へアクセスする時間帯が発生します。そのためビルダーは日時とハッシュを含む Ball 名を生成します。Ball の生成／取得／検証を先に完了し、最後に Index を切り替えます。

ローカルでは同じディレクトリ内で Index を atomic replace します。書き込みは排他ロックで直列化します。OS 強制終了・停電に対するディレクトリエントリーの完全な永続性保証はしません。中断後に Index が参照する Ball を検証し、破損時は再取得できます。

S3 では新しいキーへの Complete 完了後に、Index の PutObject に `If-Match`（初回は `If-None-Match: *`）を付けます。競合した更新が新しい Index を上書きしません。前の Ball を削除しないので、古い Index で進行中の取得も継続できます。Ball オブジェクトは本実装以外の処理で上書きしないでください。

ローカルキャッシュを Ball として保持する点は、元記事の個別ファイル保存とは異なります。これは実装依頼のローカル Ball 更新・任意アセット読み出し要件に合わせた選択であり、配置アルゴリズムは共通です。
